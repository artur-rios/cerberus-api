Purpose: implement issue20/FR-RC-04 for an owner or current read/write recipient replacing one existing encrypted record with optimistic revision checking. This is architectural work: new Domain/Data/Command/HTTP interfaces and the first cross-owner content writer. Existing all-issues authorization replaces repeated design/plan/transition approvals. ## Approaches

1. Reuse owner-only ProfileUpdateStore logic with a shared flag: reject because permission, ancestry and cross-owner lock order differ.
2. Read permission using get then update separately: reject because revocation, hierarchy and native evidence can become stale.
3. Targeted transactional authority snapshot, ordered resource locks, reload, and a guarded write: prefer; preserves native/current scope, one winner and no foreign account/profile locks. Extra bounded target-owner collection locking and SQL complexity buy a clear lock order. Complete ancestry is reevaluated inside the final write statement, without folder locks that would conflict with existing creation lock order. No general permission framework/refactor is needed.

## Transaction and races

Own actor account UPDATE -> own session UPDATE -> own selected profile UPDATE (when any) -> current eligible target-owner collections SHARE sorted publicGUID -> current recipient grants SHARE sorted publicGUID -> target record UPDATE. No foreign account/profile/protection locks. Future sharing/membership writers must honor collection->grant before affected content locks, never recipient account/profile afterward. No folder row locks: existing RecordCreateStore locks leaf-to-root folders, so adding publicGUID-ordered ancestor locks here could deadlock with concurrent creation. Initial structural permission is resolved for only one potential record before resource locks; hidden target does not lock/inspect arbitrary foreign inventory.

After waits reload current authority, target scope, complete ancestry and native evidence in one targeted SQL snapshot. Require every final contributing collection/grant to be among held validated locks; new unlocked authority rows409 reload instead of acquiring an earlier lock late. Complete ancestry/visibility is recomputed inside the final guarded UPDATE so a committed move or trash is judged at that statement, including newly visited ancestors; no stale captured folder path is trusted. Reloaded hidden scopes404 and expired authority403 take precedence. Revalidate target revision after lock; competing own/recipient writers have one winner. Final guarded UPDATE uses statement_timestamp and current actor/session/selection/owner/resource/complete recursive ancestry/collection/grant lifecycle and only validated held write routes. It cannot admit new unvalidated permissions. Zero rows classified with fresh authority/scope then safe conflict; any unexpected postwrite metadata/sequence or provider failure rolls back.

Protection rotation locks owner account/session, reads record/folder inventory without row locks, then collections UPDATE and grants UPDATE in publicGUID order, followed by optimistic stamped writes. UC19 shares that collection->grant order and does not lock owner account, avoiding reciprocal account cycles. If recipient wins after rotation read, rotation's optimistic content stamp rejects stale replacement; if rotation wins, expected revision/epoch validation rejects stale recipient update. Public RecipientKey and AuthorKey are immutable under current rotation contract; no private key/decryption involved. Concurrent lifecycle can linearize before or after update; final statement denies already committed closure/terminal state.
