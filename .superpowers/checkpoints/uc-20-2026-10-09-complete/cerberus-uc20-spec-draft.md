## Approaches

Prefer a purpose-built owner-trash transaction using existing generic TrashOperation/TrashEntry/RetentionWorkItem tables and a typed record-association snapshot. A separate read/preflight followed by mutation allows stale permissions and missing restoration links. A general permission/trash framework would widen this first operation unnecessarily. The chosen transaction has ordered parent locks and an explicit final current-scope predicate; duplicated targeted authority SQL is a maintenance cost, not a new abstraction.

## Current scope and opaque content

Use the same targeted current actor/session/selection/record/complete ancestry and eligible collection admission as UC18/19: positive matching policy/generation, issued<=statementtime, exclusive expiry or explicitly disabled renewal with null expiry, current active owned selection; selected own direct record/folder ancestor/owned linked collection or selected linked valid foreign collection; all ancestors active, owner active, global terminal exclusion conservative; relevant active cycles503, hidden404 first.

For a structurally visible foreign target, validate ALL current contributing native RO/RW collection evidence and owner/recipient public pins before403; hidden or irrelevant corrupt grants never disclose target state. Do not acquire foreign account/profile/collection locks to deny a nonowner; the targeted snapshot linearizes the denial and never authorizes a write. Owned trash requires no ciphertext decryption or encrypted-envelope parsing because it neither returns nor replaces that content. This lets owners trash damaged opaque ciphertext without pretending to repair it. Safe targetrevision/sequence, UTC normalized stored editedAt and no inconsistent active purgeAt remain required. Parent structural changes require safe revision/sequence but do not inspect their opaque content.

## Retained associations and atomic effects

New typed RecordAssociationSnapshot(Guid? FolderId,Guid[] ProfileIds,Guid[] CollectionIds), public IDs only, sorted distinct. Capture ALL stored direct owned profile/collection links, including inactive parent links, and original immediate parent. Persist only inside the restricted TrashEntry payload. Detach FolderId and remove direct ProfileRecord/CollectionRecord links in the same transaction as trash. Do not change ProfileFolder/ProfileCollection/CollectionFolder links, descendants, other records, grants or recipient-owned profiles. Inherited membership disappears from active views through the target's trash state. Selected profile survives; do not revoke or broaden its handle.

For each active directly linked owned profile/collection and active immediate folder whose direct record membership was removed, advance structuralrevision/serversequence/stamp once, preserving ciphertext/clientEditedAt/keywrappers/keyepoch. Do not bump inactive parents or inherited ancestors/recipient profiles with no direct link change. Metadata exhaustion409 and corrupt metadata503 roll back the whole operation. Each parent bump is guarded against its captured revision/sequence and current lifecycle/terminal state; a newly terminal parent cannot be silently updated. Record returned sequence need not be the last allocated global sequence because parents also advance.

Create one TrashOperation(account,record,publicrecordID,deletedAt,purgeAt), one typed TrashEntry with snapshot, one RetentionWorkItem key trash/{operationGUID} due purgeAt. Existing typed entry for an active record is a conflicting state409 rather than overwriting another operation. RestoreUC51 must reconcile/consume that entry before retrash and revalidate all retained links; grant revocation is never silently undone. No restore/list/purge endpoint or trash handler is introduced here. Existing retention executor fails/retries when a typed handler is unavailable; UC53 must install actual expiry behavior before release. Retained ciphertext remains included in actual complete protection rotation; test that missing replacement is rejected and complete rotation preserves trash/deadline/operation state.

## Lock order and races

Own actor account NO KEY UPDATE -> own session UPDATE -> union of currently stored direct owned profiles plus selected profile, sortedpublicGUID NO KEY UPDATE -> stored directly linked owned collections sortedpublicGUID NO KEY UPDATE -> immediate owned parentfolder NO KEY UPDATE if any -> targetrecord UPDATE -> existing direct ProfileRecord then CollectionRecord association rows UPDATE (stable typed order). No foreign account/profile locks and no ancestor folder locks. Account lock serializes legitimate owned create/association/rotation/lifecycle writers; collection-before-content order remains compatible with UC19 recipients and future shared-folder writers. Parent NO KEY UPDATE permits implicit FK KEY SHARE checks, avoiding the FK cycle observed in UC19; target UPDATE prevents new referencing association inserts after target admission. Actual controlled tests must prove these choices, not infer them from SQL names.

Initial snapshot verifies current actor/session/selection and target scope before discovering stored owned related sets. Acquire all profiles in one ordered query including selection, not selection first and later profiles out of order. Once the target lock excludes new reference inserts, lock its existing association rows to prevent removals between snapshot and write, then reload after all waits; current target immediateparent and all stored profile/collection IDs must be among held sets. A new association inserted before target lock acquisition is tested at that point (after target UPDATE it cannot commit); newly contributing earlier parent/link =>409/reload rather than late lock acquisition. Removed links are harmless; snapshot the actual remaining links. Recheck expiry after every relevant wait before disclosing stale revision. No old ancestry path is trusted.

Final guarded target UPDATE recomputes complete recursive current ancestry/selection/lifecycle and ownership INSIDE the database statement, matches revision/sequence/original target state, and admits only held current association/parent sets. Set deletedAt/purgeAt and detachfolder only when current authority agrees. Zero-row write is freshly classified (current denial/hidden/corrupt before conflict). Subsequent association deletion, structural parent bumps, snapshot/operation/queue persistence and postwrite verification commit together. Any injected failure after write/links/parents/entry/queue rolls back, preserving winner and a successful retry. Real recipient update versus trash has one expected-revision winner; owner rotation and same-owner graph writers serialize on account. Complete final ancestry handles committed reparent/trash/terminal changes without full ancestor locks.
