# UC14 Set profile associations

The authorized batch implements issue15, FR-PR-07/08/09 and BR-04/05/28. An owner replaces the direct record/folder and accessible collection sets on an active owned profile without transferring ownership or changing ciphertext. Existing selected access can change only its own selected profile and retain/remove currently visible direct associations; adding any new identifier requires account-wide access. A selected handle cannot widen its own permitted content by guessing another owned item GUID. This is architectural work because the first resource, grant and relationship tables are required. The existing unattended authorization replaces human stage menus; verification remains mandatory.

## Contract and failure paths

`PUT /api/profiles/{id}/associations` takes strict UTF-8 JSON with exactly `expectedRevision`, `recordIds`, `folderIds`, `collectionIds`. All arrays are required, contain distinct nonzero canonical lowercase GUIDs within each kind, and may be empty. A GUID shared across different resource kinds is allowed. Expected revision is1..9007199254740991. No query parameters, duplicate/unknown properties, numeric strings, compressed bodies or owner/context overrides.

Success200 returns `profileId`, new `revision`, new `serverSequence`, and the three resulting identifier arrays, deterministically ordered. Preserve client `editedAt`, profile envelope/wrappers/mode and every resource/grant owner and content byte. Each successful replacement, including an identical set, advances revision and sequence; stale lost-response retry returns409. Missing identity/access401; invalid current access403; malformed visible input400; hidden/missing/trashed/terminal profile or association target404; stale visible revision or counter exhaustion409; dependency/corrupt required native grant metadata503 with no data/state changes. An absent/closing/terminal account404. Profile target visibility precedes revision disclosure; references are resolved after establishing a current visible profile revision; revoked selected access denies before target lookup. AF01–05 map to these paths.

## First resource and membership schema

Add `VaultRecord`, `VaultFolder`, `VaultCollection`: common owned internal/public IDs, required opaque Envelope, Revision, UTC EditedAt, global ServerSequence and nullable DeletedAt/PurgeAt. Folder has nullable ParentFolderId; record nullable FolderId; collection has KeyEpoch. Parent references enforce the same owner using composite keys. Actual content creation, hierarchy edits and collection membership endpoints remain their subsequent UCs; no fake public CRUD is introduced here. Native encrypted names/fields and resource roots remain client-only; no plaintext field or server-usable secret is added.

Add `CollectionGrant` with unique public ID and current collection/recipient pair, recipient account FK, ReadOnly/ReadWrite access, Active/Revoked state, positive revision and required native recipient key envelope. Both active access levels permit a recipient to organize their own profile, without giving membership/deletion/sharing rights over the collection. Association admission validates actual native recipient/author/owner/resource/epoch/grant/revision binding against current public pins. Unknown access/state, invalid required material and inactive/closing/terminal owner or recipient cannot authorize a link.

Use distinct `ProfileRecord`, `ProfileFolder`, `ProfileCollection` tables with composite primary keys. Direct item links have an AccountId and composite foreign keys enforcing the profile and item share that account. Collection links can cross accounts only through a current active recipient grant. One item may appear in multiple profiles; replacement never deletes the item or another profile's links. Physical removal cascades membership rows; same-kind public IDs remain unique. Existing global ResourceId-only terminal tombstone behavior remains conservative and must be repaired before physical purge releases.

## Atomic admission and races

Follow account→session→profile locking. Check current access before visibility/revision and refresh statement time after waits. Resolve direct owned items and collections, taking collection and grant row SHARE locks in deterministic public-ID order; own account locks serialize own content changes. Refetch current rows after waits, validate native grant bindings, and recheck session time before failure/status and mutation decisions. No foreign account/profile row locks are taken. For selected sessions, requested sets must be subsets of the profile's currently visible stored sets; outside-selection identifiers return the same404. Repeat that membership predicate in the final UPDATE before replacing links. Indirectly visible descendants need account-wide access to become new direct associations.

The final profile UPDATE uses statement_timestamp() for access and rechecks all requested resource/collection/grant/owner visibility in that statement. Then replace all three link sets in the same transaction and validate the advancing safe revision/sequence before commit. Any failure rolls back metadata and links. A foreign owner can close concurrently; the final visibility predicate observes its state at the write linearization point. Grant/collection mutations must acquire their collection then grant locks and must not lock recipient account/profile rows after those locks; recipient profile visibility is filtered dynamically and later sync delivers grant/visibility removals independently. This constraint prevents an association/owner-mutation lock inversion and must carry into UC33/35–37/48.

A concurrent replacement/edit/delete has one winner; stale association writes409 if the profile remains active, or404 if trashed. With a selected handle revoked by deletion,403 takes priority. Lock-wait and immediately-prewrite expiry never commit. Missing or hidden IDs never create partial links.

## Integrate existing profile flows now

Profile creation accepts resolvable nonempty sets using the same admission rules/locks and final visibility checks, rather than its previous unresolved-only guard. Account-wide access remains required for creation.

Get and list project only currently visible association IDs in the same SQL snapshot as account/session/profile authorization and pagination. Direct links require active own items; collections require active owner/account/collection and current owned-or-active-grant permission. Hidden, trashed, terminal, revoked or closing-owner links are omitted. Lists gain the three arrays on each item; existing envelope, cursor and ordering-corruption checks remain. No extra query per item and no total-count leak. Current grant rows authorize ID visibility; no grant ciphertext is returned here. Native key material is validated when admitting or rotating grants, and forthcoming grant writes must preserve that invariant.

Profile trash snapshots actual stored identifier sets, removes all its associations, and retains underlying resources, grants and other profiles' links. Snapshot can include retained but currently hidden memberships; future restoration must revalidate all targets/grants/deadlines and never revive stale access. Operation/queue/selected-revocation semantics remain UC13's transaction.

## Complete native rotation inventory now

Extend `ContentReplacement` to account/profile/record/folder/collection. Only profiles carry ProfileKeyWrappers; other kinds reject them. A rotate-content request must replace every retained owned resource, including trash, plus the account and profiles; no missing/extra/duplicate/foreign entries. Validate current native envelope shape/counters and new epoch=current+1 with fresh salt and nonce before consuming proof. Preserve EditedAt and ownership, advance revision/sequence, and update collection KeyEpoch to the new envelope epoch. Rewrap changes no content and accepts no resource/grant replacements.

Add strict `CollectionGrantReplacement(GrantId,ExpectedRevision,KeyEnvelope)` and an additive `GrantReplacements` array on ProtectionChange, defaulting to empty for existing requests. Rotation must replace exactly all active grants on owned collections (not received or revoked grants), including any retained collection, binding native envelopes to the recipient's current public pins, owner author pin, collection/new epoch and grant/new revision. Validate current wrappers and replacement contexts before proof consumption; rotate all content/protection/grants atomically. Revoked recipients receive no newly wrapped roots. Future grant creation/deactivation must use the established locks and completeness contract. No new cryptographic primitives or decryption are introduced.
