# UC23 create folder design

Issue 24 implements UC-23, FR-FD-01, BR-07/22 (issue tracing), with BR-04/10/15 ownership/encryption/scope constraints. The owner submits an encrypted name envelope and permitted public relationships; the server creates owned content and returns public metadata. This is the next unit in the authorized unattended batch. Independent formal security/protocol and real-client qualification remain development-only deferred; main/tag/release gates remain mandatory.

Use the existing VaultFolder, ProfileFolder and ParentFolderId schema with Domain/Folders contracts, Data/Folders store, Command/Folders boundary and a dedicated FoldersController. No new migrations, dependencies, encryption scheme or collection-membership operation. Reusing the record store through a generic public resource abstraction would broaden this change without reducing admission risk; a focused folder implementation follows the established pattern. Restricting creation to account-wide handles would prevent profile-password owners from creating content, while accepting arbitrary relationships from selected access would broaden authority.

POST /api/folders requires exactly folderId, envelope, editedAt and profileIds; parentFolderId is optional nullable. IDs are canonical nonzero lowercase UUIDs at HTTP; profileIds is nonnull, unique and nonzero. Initial native cerberus-content-v1 envelope epoch must be 1. No plaintext name, owner, internal ID, grant, collectionIds, expectedRevision or access credential in the body. ParentFolderId equal to FolderId is an invalid self-parent request (400). The output has exactly folderId/revision/serverSequence/editedAt, revision 1 and a positive protocol-safe server sequence. Accept UTC editedAt at least 10 ticks and floor to microseconds BEFORE PostgreSQL binding, including pre-2000 and maximum supported timestamps. Names remain required inside client-encrypted content; the API cannot inspect their plaintext.

An active current account-wide session may create a root without profiles, or directly associate the NEW folder with zero or multiple owned active profiles and an optional owned active parent. A current selected session requires exactly its selected profile in profileIds: empty is 403; another/multiple profile is hidden 404. Its parent must already be visible through a direct ProfileFolder on the owned active ancestry or an active OWN collection attached to the selected profile and containing that ancestry. A foreign collection grant never grants parent/membership administration or ownership. Both native recipient modes cannot create under another owner's folder, yielding nonrevealing 404. The new direct link makes root creation usable without adding existing content to other selections.

One database transaction: account FOR UPDATE, current session FOR UPDATE, requested owned profiles in public UUID order, then owned parent/ancestors. Current owned writers serialize at the account lock; no foreign account/profile/grant lock is added. Session/account lifecycle, typed account/profile/folder terminal identity, current policy and generation, issued time and exclusive database-time expiry are checked after waits. Parent traversal requires complete same-owner active nonterminal ancestry; missing/foreign/trash/terminal parent or ancestor returns 404. Cyclic corrupt ancestry fails closed; selected callers without a contributing current owned route receive hidden 404, while visible required cyclic ancestry is 503. No ciphertext or unused ancestor metadata is parsed. Reject counter corruption only on directly affected profiles/immediate parent (503), saturated revision or sequence exhaustion (409). Existing/trash/foreign/typed-terminal FOLDER UUIDs are reserved (409); same UUID in another resource kind remains independent.

The final INSERT SELECT rechecks current account/session/selected profile and exactly the resolved profile/parent ancestry and selected owned-collection route at statement_timestamp, after validation and waits. Recheck terminal reservation here; a lost guarded insert diagnoses current authorization/hidden relationship before conflict. Insert one folder and direct ProfileFolder rows, preserving existing links. Advance each directly linked profile and only the immediate parent revision/server sequence/concurrency stamp once, preserving their ciphertext/wrappers/client EditedAt. Ancestors and profiles reached only dynamically receive no fabricated direct change. Additive creation has no expected parent revision input; held rows and changed metadata make later cached replacement writers conflict normally. Validate inserted metadata before commit. Any link/write/projection/sequence/dependency failure rolls back the entire folder, links and parent changes; same-ID retry is safe. Caller cancellation propagates and rolls back; internal dependency cancellation maps to 503.

The existing protection-rotation inventory already includes folders; actual newly created-folder tests must prove missing inventory fails before proof consumption and complete inventory rotates folder ciphertext/revision without changing editedAt or parent structure. Profile get/list must include active new direct FolderIds. Existing record ancestry and reads must accept real newly created parents. Descendant access evolves dynamically; durable offline inherited visibility and key provisioning remain later synchronization and client-release integration, not certified by these server fixtures.

HTTP uses the existing VaultProofBody strict bounded UTF-8 parser: no BOM, compression, duplicate/unknown/case-variant JSON members, numeric strings, invalid envelopes or malformed identifiers; no query and exactly one canonical access header. Trusted actor comes from current Heimdall identity. Common no-store applies on every outcome and oversized input produces empty 413. Map folder_created to 201, validation_failed 400, authentication_required/vault_access_required 401, vault_access_denied 403, not_found 404, revision_conflict 409 and persistence_unavailable 503; unknown store errors and malformed success become safe 503 with no payload.

AF mapping: AF-01 strict input/envelope/relationship/self-parent 400 (common oversized 413); AF-02 hidden account/profile/parent/ancestor 404; AF-03 current identity 401 or provider 503, missing handle 401, malformed 400, expired/revoked/policy/generation/invalid selection 403; AF-04 duplicate/reserved folder ID, concurrent duplicate winner or exhausted affected revision/sequence 409; AF-05 dependency or necessary corrupt state 503, atomic rollback and retry. Every failure must assert unchanged persisted state.
