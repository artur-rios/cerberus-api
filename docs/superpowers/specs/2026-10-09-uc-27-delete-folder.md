## Alternatives and selected architecture

A per-item RecordTrashStore loop creates multiple operations/deadlines and risks partial cascades, so reject it. A one-shot unguarded recursive UPDATE can miss new membership, current expiry and concurrent native edits, so reject it. Use a dedicated FolderTrashStore with current root authority adapted from FolderUpdateStore, a bounded recursive subtree inventory, ordered structural locks, one guarded root write and same-time guarded child/record writes, then one operation/many typed entries/one retention item. No schema/dependency/algorithm changes; introduce a typed FolderAssociationSnapshot matching existing RecordAssociationSnapshot restoration requirements.
