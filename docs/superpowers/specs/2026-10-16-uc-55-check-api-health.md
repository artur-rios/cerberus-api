# UC55 operational health design

Intent: operators and monitors need process/dependency signals without vault identities or protected diagnostics. Implement UC55 and AF01–03, FR-OP-01–03 and NFR12, preserving the SRS matrix (including explicitly granted software and separately granted people). Existing unattended batch authorization replaces the human gates; this architectural addition gets written design/plan, inline TDD, one fresh final review and normal verified develop integration. No release/deployment qualification.

Alternatives considered: framework-only default health checks expose no adopted operational authorization or restore semantics; a broad shared authentication rewrite risks unrelated endpoints. Select focused probe/auth services and three explicit controller actions with narrow health metadata. No new package, database migration, identity mutation or maintenance endpoint.

## Wire and lifecycle
GET /health/live is public, always200 with exactly {"status":"healthy"}, independent of DB/provider/restore. GET /health/ready is public200 healthy or503 unhealthy, exactly one status member. Both ignore supplied identity, headers and query options: none opt into details. GET /health/details requires actual caller-bound operational authorization and returns200/503 {status,components}; components is exactly database,identity,restore, each {name,status,elapsedMilliseconds}, fixed healthy/unhealthy states and nonnegative measured durations. No URLs, connection configuration, subject IDs, payloads, exception types/messages/stacks or credentials. GET has no request model. Standard request byte limits and global no-store remain; no ETag/LastModified. Authentication errors use existing safe ProcessOutput401(authentication_required),403(operational_access_required),503(identity_unavailable), without components.

Only these three marked health actions bypass a closed restore barrier; details still authenticates. Vault routes remain503 while reconciliation is required. Probe restore is healthy when RestoreRequired is false or gate ready. Recheck the gate after dependency probes. This is an observed health result, not a distributed instantaneous guarantee.

## Dependency checks
Readiness/details share an application service. Probe database via a dedicated factory-owned connection/context executing SELECT public_id FROM cerberus.account LIMIT 0: verifies configured connection, account schema and SELECT capability without loading user rows or mutations; it is not an exhaustive schema-integrity or write-capability certification. Probe configured non-user Heimdall scope/service authority using existing VerifyScopeAsync (GET scope then GET service owner). Never login, register or use a public caller's credential for readiness. Independently report both dependency results. Each probe has a five-second cooperative cancellation budget, plus existing lower transport limits; cancellation of the request propagates, expected dependency exceptions become unhealthy, protected text is never returned/logged. Dispose each database resource. No caching, retries or scheduled probes; no numerical SLO is invented.

## Explicit operational grants
Add optional CERBERUS_OPERATIONAL_PERSON_IDS and CERBERUS_OPERATIONAL_APPLICATION_IDS (configuration aliases Cerberus:OperationalPersonIds / OperationalApplicationIds), separate comma-separated canonical lowercase nonzero D UUID allowlists. Missing/empty means no grants. Reject malformed, whitespace, empty entries and duplicates at startup without echoing values. Typed subjects prevent equal UUIDs crossing human/software grants. Configuration changes require normal restart; no vault grant implies operational privilege.

Signed people must have configured human audience/issuer/current lifetime, no pending MFA, tokenKind, credentialId or mixed authority aliases, unique JSON claim keys, canonical subject and roleId3/configured scope OR roleId2/configured scope among unique ownedScopeIds. Role2 may own multiple scopes; configured service validation remains unchanged. Never use a global admin fallback. Applications use the existing strict distinct-audience application validator. A valid signed actor without its separate configured grant gets403 without component/dependency probes. Invalid/absent/mixed bearer gets401. Granted people are revalidated using actual caller bearer GET person and (role2) GET configured scope; current subject/role/deletion/scope ownership must match, then token is revalidated after the network wait. Granted applications use existing GET /api/applications/self current credential contract. Dependency outage gives safe503; revoked/deleted identity401. Configured service credential is never substituted for the detailed caller.

## Verification and limits
AF01: anonymous/minimal probes, ignored detail opt-ins, no identity/database calls for liveness, healthy/degraded readiness. AF02: missing/invalid/expired/wrong-scope/mixed tokens, ungranted owner/operator/application, cross-kind UUID grants, granted role3/role2 multi-scope/application, live denial/outage, actual bearer routes and no user authentication probes. AF03: real database down/schema/SELECT denial, provider failures/stalls, both observed independently, cancellation/resource cleanup, restore closure during probe and closed gate HTTP isolation. Check native graph unchanged and raw JSON/OpenAPI closed contract. Existing unrelated account404 schema discrepancy stays deferred.
